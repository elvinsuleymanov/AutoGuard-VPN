## peer-watcher.sh

The WireGuard container runs `peer-watcher.sh` on startup. It:

1. Waits in a loop until `wg show wg0` succeeds.
2. Writes `wg show wg0 public-key > /config/keys/server_public.key`.
3. Loads all existing `*.conf` files from `/config/peers/` via `wg addconf`.
4. Enters an `inotifywait -m -e close_write` loop — on each new `.conf` file, calls `wg addconf wg0 <file>`.

No container restart is ever needed to activate new peers.

The `peers/` directory is bind-mounted into both containers:
- `auth-service`: `/app/peers` (writes peer configs here)
- `wireguard`: `/config/peers` (peer-watcher reads from here)

## IP Allocation

```python
def allocate_ip() -> str:
    base = INTERNAL_SUBNET.rsplit(".", 1)[0]
    used = _get_used_ips()
    for i in range(2, 255):
        candidate = f"{base}.{i}"
        if candidate not in used:
            return candidate
    raise RuntimeError("No available IP addresses")
```

The server holds `10.13.26.1`. Clients are allocated `.2` through `.254` (253 max). Used IPs are determined by scanning `AllowedIPs` lines in all existing `*.conf` files in `/app/peers/`.

## Public Key Validation

```python
def is_valid_wg_pubkey(key: str) -> bool:
    if not re.fullmatch(r'[A-Za-z0-9+/]{43}=', key):
        return False
    decoded = base64.b64decode(key)
    return len(decoded) == 32
```

An X25519 public key is 32 bytes. Base64-encoded it produces 44 characters (43 + one `=` padding). The validator checks both the character pattern and the decoded length.

## Peer File Format

Each registered peer is stored at `./peers/<sha256-of-pubkey[:16]>.conf`:

```ini
[Peer]
PublicKey = <client-public-key>
AllowedIPs = 10.13.26.X/32
```

Note the asymmetry with what the **client** receives, which is
`AllowedIPs = 0.0.0.0/0, ::/0`. The two directions of `AllowedIPs` mean
different things: on the server it is cryptokey routing — the only source
address this peer is permitted to use — while on the client it selects which
destinations enter the tunnel. The server side stays a single IPv4 `/32`
deliberately.

## Why the client claims `::/0`

The tunnel carries no IPv6 at all: client `Address` is an IPv4 `/32` and the
server has no IPv6 address. `::/0` is in the client's `AllowedIPs` to
**blackhole** IPv6, not to transport it.

Without it, `AllowedIPs = 0.0.0.0/0` claims IPv4 only, and on a dual-stack
client every IPv6-capable destination is reached straight out the normal
interface — exposing the real address while the VPN appears to be working
correctly. Claiming the whole v6 range instead pulls a default IPv6 route into
an interface that cannot route it, so those packets die locally.

Anything that does reach the server is dropped there anyway, because the peer
file above permits only that one IPv4 source.

## Nginx TLS Termination

```nginx
geo $allowed_source {
    default 0;
    include /etc/nginx/geo/allow.conf;
}

server {
    listen 443 ssl;
    server_name <public-ip>;

    if ($allowed_source = 0) {
        return 444;
    }

    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers HIGH:!aNULL:!MD5;
    ssl_session_tickets off;

    location / {
        proxy_pass http://auth-service:5000;
    }
}
```

`proxy_pass` targets the **service name**, not a container IP — Docker's embedded
DNS resolves it on the user-defined bridge, so the config survives an address
change.

### The geo gate

`allow.conf` is generated by `setup.sh`. Without `--geo-allow` it holds a single
`0.0.0.0/0 1;` line, so `$allowed_source` is `1` for everyone and the gate is a
no-op. With country codes supplied it holds their aggregated CIDR blocks plus
loopback, the Docker bridge and the VPN subnet.

`444` is nginx's non-standard "close the connection with no response at all",
which gives a blocked scanner nothing to fingerprint. `if` is safe in this
position because `return` is one of the few directives it handles correctly.

### Exposed surface

`location /` proxies everything, so both FastAPI routes are reachable from the
internet — subject to the geo gate:

| Route | Auth | Purpose |
|---|---|---|
| `POST /addnewpeer` | `X-Auth-Token`, compared with `secrets.compare_digest` | Peer registration |
| `GET /health` | none | Liveness; also what the nginx container healthchecks |

Every other path returns FastAPI's 404. There is no filesystem served and no
second application behind this proxy, which is why the constant background
scanning any public address attracts finds nothing.

## server_public.key Lifecycle

1. `setup.sh` generates the keypair and writes `./wireguard/keys/server_public.key`.
2. `peer-watcher.sh` re-writes it on WireGuard startup via `wg show wg0 public-key`.
3. auth-service mounts it read-only at `/wg-keys/server_public.key`.
4. `helpers.py` reads it on every `/addnewpeer` request to include in the returned client config.

The `depends_on: wireguard: condition: service_healthy` constraint guarantees WireGuard (and therefore the key file) is ready before auth-service starts.
