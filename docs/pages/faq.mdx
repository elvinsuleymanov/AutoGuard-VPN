# FAQ & Troubleshooting

## Clients have no internet after connecting

The masquerade rule in `wg0.conf` targets `eth0`:

```
PostUp = iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE
```

That rule runs **inside** the WireGuard container, and a container on a single
user-defined bridge always sees its interface as `eth0`. So the host's interface
name (`ens5` on AWS Nitro, `enX0` on Amazon Linux 2023, …) does not matter here.

Confirm before chasing it further:

```bash
docker exec wireguard ip link show
docker exec wireguard iptables -t nat -L POSTROUTING -n -v
```

If the interface genuinely is not `eth0`, edit `templates/wg0.conf.template`
(not the rendered `wireguard/wg_confs/wg0.conf`, which is overwritten on every
`setup.sh` run), then:

```bash
./setup.sh && docker compose restart wireguard
```

Otherwise check `net.ipv4.ip_forward` on the host and that your cloud firewall
allows outbound traffic.

## "The server presented a different certificate than the one this script was generated for"

The script pins the server's certificate key and refused to send anything,
because the server presented a different one. Two causes:

- **The certificate changed.** `setup.sh --force`, or a run with a new
  address, issues a new certificate. Scripts rendered before that no longer
  match — use the fresh ones from `scripts/`.
- **Something is intercepting the connection.** If the certificate did not
  change, do not work around this; try from another network.

## Registration fails with an SSL certificate error

On a self-signed server the scripts pin the certificate rather than validate it,
so this should not happen. If you see it **after** installing a real
certificate, the scripts were rendered before it was in place. Re-run
`./setup.sh` and redistribute `scripts/`; the run should report `CA-signed
certificate — client scripts will validate TLS normally.`

When calling the API manually against a self-signed server, pin it the same
way. `setup.sh` prints the fingerprint as `sha256//<pin>`:

```bash
curl -sS -k --pinnedpubkey "sha256//<pin>" -X POST \
  -H "Content-Type: application/json" \
  -H "X-Auth-Token: <token>" \
  -d '{"public_key":"..."}' \
  https://<SERVER>/addnewpeer
```

On Windows, call `curl.exe` explicitly with the same flags — in Windows
PowerShell 5.1, plain `curl` is an alias for `Invoke-WebRequest`.

## `docker compose up` fails before running setup.sh

`.env` is generated, not committed. Docker Compose cannot interpolate variables
like `${IP_WG}` until `setup.sh` writes it. Always run `./setup.sh` first.

## Is it safe to re-run `setup.sh`?

Yes. Every generated file is rendered fresh from `templates/` on each run, and
the secrets in `.env` plus the keypair in `wireguard/keys/` are reused, so
existing clients keep working.

Pass `--force` only when you intend to rotate the server keypair, registration
token, and Pi-hole password — that invalidates every client config already
handed out.

## Pi-hole admin page is not accessible

The admin UI is bound to `127.0.0.1:65231` on the host, so it is deliberately not
reachable from the internet. Get to it either over the VPN:

```
http://172.29.144.30/admin
```

or through an SSH tunnel:

```bash
ssh -L 65231:127.0.0.1:65231 <user>@<server-ip>
# then open http://127.0.0.1:65231/admin
```

- Retrieve the generated password: `grep WEBPASSWORD .env`
- Check the container state: `docker compose ps pihole` and `docker compose logs pihole`

> Do not "fix" this by changing the publish back to `65231:80`. Docker's published
> ports are DNAT'd in nat/PREROUTING and skip the host `INPUT` chain, so `ufw`
> rules will not hold it back — the bind address is the only thing protecting it.

## I lost all internet after the VPN dropped

That is the kill switch working as designed. Clients block traffic that cannot
go through the tunnel rather than letting it fall back to your normal
connection — which is the whole point, since a silent fallback is exactly how a
VPN leaks your real address without you noticing.

**Get back online** by bringing the tunnel down cleanly, which runs `PreDown`
and removes the rules:

```bash
sudo wg-quick down wg0
```

On Windows, Deactivate the tunnel in the WireGuard GUI.

If a clean `wg-quick down` does **not** restore connectivity, rules were left
behind by a bring-up that died partway. Remove them by hand:

```bash
sudo iptables  -S OUTPUT | grep -- '-j REJECT'   # find them
sudo iptables  -D OUTPUT <rule-number>
sudo ip6tables -D OUTPUT <rule-number>
```

Note that this also blocks **LAN access** while connected — printers, network
shares, router admin pages. That is inherent to blocking everything outside the
tunnel, not a bug.

## Can I still reach my local network while connected?

No, not with the kill switch installed. It rejects all output that is not
leaving through the tunnel, and your LAN is not.

A LAN exemption is possible — an `iptables` rule accepting your local prefix
ahead of the REJECT — but it widens the leak surface, because anything that can
reach that prefix bypasses the VPN. Decide it deliberately rather than by
default. The hooks live in `templates/setupclient.sh.template`; edit the
template, not the rendered `scripts/`, which is regenerated on every
`setup.sh` run.

## My IPv6 test site still shows my real address

Check the tunnel actually claimed IPv6:

```bash
sudo wg show wg0 allowed-ips      # expect 0.0.0.0/0 and ::/0
ip -6 route show dev wg0
```

If `::/0` is missing, your config predates the IPv6 fix — configs are generated
at registration and existing peers are never rewritten. Re-register the client
(delete the peer server-side first, per
[Client Setup](/client-setup)) or add `::/0` to `AllowedIPs` by hand.

The tunnel is IPv4-only, so `::/0` is there to blackhole IPv6, not carry it.
Without it a dual-stack client sends IPv6 straight out its normal interface.

## My logs are full of requests for `.env`, `wp-config.php`, `phpinfo.php`

That is internet background noise, not a targeted attack. Every public IPv4
address is swept within minutes of coming up, and the request list is a generic
WordPress/Laravel/Django wordlist aimed at nobody in particular.

Check the status codes before worrying: they will all be `404`, with a 22-byte
body — FastAPI's `{"detail":"Not Found"}`. There are only two routes behind the
proxy and no filesystem is served, so there is nothing to find.

The `127.0.0.1 … "GET /health" … curl/…` lines at a regular interval are your
own nginx container healthchecking itself.

To cut the noise down, restrict the API by country:

```bash
./setup.sh --geo-allow az
```

Blocked sources then get nginx `444` — connection closed, no response — instead
of being proxied through to the application. The requests still appear in the
access log, but as one-line `444`s. Note this gates only the registration API;
the WireGuard port is unaffected, so a client abroad cannot *register* until it
is back inside an allow-listed country.

## nginx-proxy is unhealthy

Get the actual error first — the exit code identifies the cause immediately:

```bash
docker inspect --format '{{range .State.Health.Log}}exit={{.ExitCode}} {{.Output}}{{end}}' nginx_proxy
```

| Exit code | Meaning |
|---|---|
| `22`, `60`, `77` | A stale container is still running an older healthcheck definition |
| `52` | Empty reply — nginx returned `444`, so the geo allow-list is blocking the healthcheck itself |
| `7` | Connection refused — nginx never started; check `docker compose logs nginx-proxy` |
| `127` | `curl` missing from the image |

<Callout type="warning">
  A healthcheck is baked into a container at creation. `docker compose restart`
  restarts the process inside the *existing* container and does **not** pick up
  a changed `healthcheck:` block. Recreate it instead:

```bash
docker compose up -d --force-recreate nginx-proxy
```
</Callout>

## The Windows client failed the first time, then worked

Fixed as of the current script — if you are still seeing it, re-render and
redistribute `scripts/setupclient.ps1`.

The WireGuard MSI installs the binaries but does not create
`C:\Program Files\WireGuard\Data\Configurations`; the `WireGuardManager` service
creates it on its first start, and a `--silent` install never launches the GUI to
trigger that. The first run therefore found no config store. By the second run
the service had started on its own.

The script now waits for that directory **before** contacting the server. That
ordering matters: the old version registered the peer first, so every failed
first run left an orphaned peer file holding an address that
`allocate_ip()` would never hand out again.

If you hit this on an older script, clean up the abandoned peer:

```bash
cd ~/AutoGuard-VPN
grep -l '10\.13\.26\.2/32' peers/*.conf
PUB=$(awk '/PublicKey/{print $3}' peers/<file>.conf)
docker exec wireguard wg set wg0 peer "$PUB" remove
rm peers/<file>.conf
```

## WireGuard container is unhealthy

The healthcheck runs `wg show wg0` — it fails if `wg0` is not up.

```bash
docker compose logs wireguard
```

Common causes:
- `wg0.conf` still contains the `your-private-key` placeholder (setup.sh patching failed)
- Kernel module not loaded on the host: `modprobe wireguard`

## auth-service exits immediately

Check that `REGISTRATION_TOKEN` is present in `.env` — auth-service calls `os.environ["REGISTRATION_TOKEN"]` at import time and crashes if the variable is missing.

Check that `server_public.key` is non-empty: `cat ./wireguard/keys/server_public.key`

## Port 53 conflict warning

AutoGuard VPN does not expose port 53 to the Docker host. Pi-hole listens on `172.29.144.30:53` inside its container and Unbound on `0.0.0.0:5053` inside its container — neither binds to the host's port 53. Any port 53 conflict you see is from another service on the host (e.g. `systemd-resolved`) and does not affect this stack.

## New peer is not appearing in `wg show`

`peer-watcher.sh` may have exited:

```bash
docker exec wireguard ps aux | grep peer-watcher
docker compose restart wireguard
```

Also verify the `peers/` directory is correctly mounted in both containers:

```bash
docker inspect wireguard | grep -A5 Mounts
docker inspect auth_service | grep -A5 Mounts
```

## Maximum number of clients

The `10.13.26.0/24` subnet supports **253 peers** (`10.13.26.2` through `10.13.26.254`). Old entries in `./peers/` consume slots even if the client is gone. Remove stale peers manually:

```bash
rm ./peers/<sha256-prefix>.conf
docker exec wireguard wg set wg0 peer <public-key> remove
```
