# Client Setup

After `setup.sh` runs on the server, `scripts/setupclient.sh` and
`scripts/setupclient.ps1` are ready to distribute. Both already contain your
server address and registration token — copy the right one to the client and run
it with root or Administrator rights.

Phones and tablets have no script: you add them from the server with
`add-device.sh` — see [Phones and tablets](#phones-and-tablets).

<Callout type="warning">
  These rendered scripts hold a live bearer token and are gitignored for that
  reason. Move them over a channel you trust. If one leaks, rotate with
  `./setup.sh --force` — that invalidates every config already issued.
</Callout>

## The registration handshake

Both scripts follow the same five steps, and the ordering is the part that
matters for security:

<Steps>

### The keypair is generated locally

`wg genkey` on the client. **The private key never leaves the device** and is
never transmitted, logged, or stored on the server.

### Only the public key is sent — and only to your server

A single `POST` to `https://<server>/addnewpeer` carrying the public key and the
`X-Auth-Token` header. Before sending it, the script checks that the server
presents the certificate key `setup.sh` pinned into it, and aborts otherwise — see
[How the script recognises your server](#how-the-script-recognises-your-server).

### The server allocates an address

`auth-service` scans existing peer files for used addresses, takes the first
free one in `10.13.26.2`–`10.13.26.254`, and writes the peer file. `peer-watcher.sh`
picks it up through `inotifywait` and applies it with `wg addconf` — no restart,
no dropped peers.

### The client builds its own config

Only the assigned address is taken from the reply, and it must fall inside
`10.13.26.0/24`. The server's WireGuard key, endpoint and DNS come from values
`setup.sh` wrote into the script, so a forged reply cannot point the tunnel at
another server. The private key from step 1 goes straight into that config.

### The tunnel comes up

The config is written with restrictive permissions and the interface is started.

</Steps>

## Linux

### Prerequisites

```bash
sudo apt install wireguard-tools curl python3 iptables
```

On RHEL/Fedora:

```bash
sudo dnf install wireguard-tools curl python3 iptables
```

<Callout type="info">
  Unlike the Windows script, the Linux one does not install its own
  dependencies — it checks for `wg`, `curl`, `python3` and `iptables`, and exits
  with an install hint if any is missing. `iptables` is required because the
  kill switch is built from `iptables` rules. On nftables-only systems the
  `iptables-nft` shim satisfies this; a host with neither will fail the check
  with a clear message rather than installing a tunnel with no leak protection.
</Callout>

### Run

```bash
chmod +x setupclient.sh
sudo ./setupclient.sh
```

### What it does

1. Requires root, then checks `wg`, `curl`, `python3` and `iptables` are in
   `PATH`, and detects whether the kernel has IPv6 (`/proc/net/if_inet6`).
2. Turns off starting the VPN at boot (`wg-quick@wg0`) if an earlier version
   of this script enabled it.
3. **If `/etc/wireguard/wg0.conf` already exists** → turns the VPN on if it is
   off, and exits. Re-running is safe and does not register a second peer.
4. Generates the keypair: `wg genkey`, then `wg pubkey`.
5. Registers with the server, pinning its certificate key (on a CA-signed
   server `-k --pinnedpubkey` is left out and curl validates normally):
   ```bash
   curl -sS --max-time 30 -k --pinnedpubkey "sha256//<pin>" -X POST \
     -H "Content-Type: application/json" \
     -H "X-Auth-Token: <token>" \
     -d '{"public_key": "<pubkey>"}' \
     https://<SERVER_IP>/addnewpeer
   ```
6. Parses the JSON with `python3`, requires `status == "ok"`, and requires the
   assigned address to be inside `10.13.26.0/24`.
7. Builds the config from the values `setup.sh` baked in, injects the kill
   switch hooks into the `[Interface]` section, and writes
   `/etc/wireguard/wg0.conf` with mode `600`.
8. Turns the VPN on with `wg-quick up wg0`. It stays on until you turn it off
   or restart; nothing starts it at boot. **If bring-up fails, the script tears
   the interface back down.** In the rare case that still leaves you without
   internet, a kill switch rule was left behind — restart, or see
   [I lost all internet after the VPN dropped](/faq#i-lost-all-internet-after-the-vpn-dropped).

### The generated config

```ini
[Interface]
PrivateKey = <client-private-key>
Address = 10.13.26.X/32
DNS = 172.29.144.30
PostUp  = iptables  -I OUTPUT ! -o %i -m mark ! --mark $(wg show %i fwmark) -m addrtype ! --dst-type LOCAL -j REJECT
PreDown = iptables  -D OUTPUT ! -o %i -m mark ! --mark $(wg show %i fwmark) -m addrtype ! --dst-type LOCAL -j REJECT
PostUp  = ip6tables -I OUTPUT ! -o %i -m mark ! --mark $(wg show %i fwmark) -m addrtype ! --dst-type LOCAL -j REJECT
PreDown = ip6tables -D OUTPUT ! -o %i -m mark ! --mark $(wg show %i fwmark) -m addrtype ! --dst-type LOCAL -j REJECT

[Peer]
PublicKey = <server-public-key>
Endpoint = <SERVER_IP>:51820
AllowedIPs = 0.0.0.0/0, ::/0
PersistentKeepalive = 25
```

`AllowedIPs = 0.0.0.0/0, ::/0` claims both address families. `DNS` points at
Pi-hole inside the Docker bridge, reachable only once the tunnel is up.

The `PostUp`/`PreDown` hooks are added by `setupclient.sh` on the client, not
by the server. WireGuard for Windows rejects configs containing them unless
script execution is enabled in the registry, so shipping them from the server
would break every Windows client.

### The kill switch

Those four rules are the kill switch. While the VPN is on, they reject any
output that is not leaving through the tunnel, and they stay installed until
`PreDown` removes them — so if the interface disappears without a clean
`wg-quick down`, traffic is blocked rather than falling back, while turning the
VPN off with `wg-quick down` restores normal connectivity.

Two clauses do the real work, and removing either breaks it:

| Clause | Purpose |
|---|---|
| `! --mark $(wg show %i fwmark)` | Exempts WireGuard's own handshake packets, which carry that mark. Without it the rule blocks the tunnel it is protecting. |
| `! --dst-type LOCAL` | Exempts traffic to this machine's own addresses, loopback included. Without it, local services break — such as the `systemd-resolved` DNS stub on `127.0.0.53`. |

What happens in each state:

| State | Result |
|---|---|
| VPN on, interface removed without a clean `wg-quick down` | **Blocked.** This is the kill switch. |
| VPN on, server unreachable | Blackholed by routing — traffic never leaves anyway. |
| VPN off — after `wg-quick down`, or after a restart | Nothing blocked. Normal connection, no VPN. |

The kill switch protects only while the VPN is on. The rules live in memory, and
nothing starts the VPN at boot, so after a restart the machine uses your normal
connection until you turn the VPN on again.

<Callout type="warning">
  The kill switch blocks **LAN access too** — local printers, SSH to machines on
  your network, router admin pages. That is what "block everything not in the
  tunnel" means. To get back on your local network, bring the tunnel down
  cleanly with `sudo wg-quick down wg0`.
</Callout>

### IPv6

The tunnel is IPv4-only: `Address` is a `/32` and the server has no IPv6. `::/0`
is therefore in `AllowedIPs` to **blackhole** IPv6, not to carry it — it pulls a
default IPv6 route into an interface that cannot route it, so those packets die
locally. Without that line, a dual-stack client sends IPv6 straight out its
normal interface and exposes its real address while everything appears to work.

If the kernel has no IPv6 at all, `setupclient.sh` detects it (`/proc/net/if_inet6`
is absent), leaves out `::/0` so `wg-quick` can start, and skips the `ip6tables`
hooks. Nothing can leak over a stack that is not there.

### Turning it on and off

The VPN is on only when you turn it on. It stays on until you turn it off or
restart, and it does not start by itself after a restart.

```bash
sudo wg-quick up wg0      # turn the VPN on
sudo wg-quick down wg0    # turn it off, and restore normal connectivity
sudo wg show wg0          # is it on? peers, handshakes, transfer counters

sudo iptables  -S OUTPUT | grep REJECT   # confirm the kill switch is installed
sudo ip6tables -S OUTPUT | grep REJECT
```

Re-running `sudo ./setupclient.sh` on a configured device also turns it on.

## Windows

### Prerequisites

- Windows 10 or 11, PowerShell 5.1 or newer
- An **Administrator** PowerShell session — the script declares
  `#Requires -RunAsAdministrator` and will refuse to run otherwise
- WireGuard for Windows — installed automatically via `winget` if absent

### Run

Open PowerShell as Administrator:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
.\setupclient.ps1
```

<Callout type="info">
  `-Scope Process` limits the policy change to this window only; nothing
  persists after you close it.
</Callout>

### What it does

1. **Installs WireGuard if needed** — checks for
   `C:\Program Files\WireGuard\wg.exe`, otherwise runs
   `winget install -e --id WireGuard.WireGuard --silent`.
2. **Waits for the config store.** The MSI does not create
   `C:\Program Files\WireGuard\Data\Configurations` — the `WireGuardManager`
   service creates it on its first start, and a silent install never launches
   the GUI to trigger that. The script starts the service and waits for the
   directory before going any further.
3. **Exits early if the tunnel already exists.** If `wg0.conf` or
   `wg0.conf.dpapi` is already in the store, it opens the GUI and stops — it
   will not register a second peer.
4. Generates the keypair with `wg.exe genkey` and `wg.exe pubkey`.
5. Registers — through the built-in `curl.exe` with the certificate key pinned,
   or through `Invoke-RestMethod` when the server's certificate is CA-signed —
   checks the assigned address is inside `10.13.26.0/24`, then removes any
   tunnel an older version of this script installed from
   `C:\ProgramData\WireGuard`.
6. Builds the config from the values `setup.sh` baked in, writes it into the
   store, and grants `SYSTEM` and `Administrators` access with `icacls`.
7. **Imports it into the manager** by restarting `WireGuardManager` and waiting
   for the plaintext `wg0.conf` to become the encrypted `wg0.conf.dpapi`. That
   conversion is what makes the tunnel appear in the GUI.
8. Installs the tunnel service with `wireguard.exe /installtunnelservice`.
9. **Verifies a real handshake** for up to 15 seconds. If none arrives the
   script deactivates the tunnel so it cannot blackhole your internet, leaves it
   listed in the GUI to retry, and prints your peer public key for debugging.
10. **Verifies the kill switch** by confirming both default routes point at the
    WireGuard adapter. Reports what it finds; never fails the install.

<Callout type="info">
  The config goes into the **GUI store** rather than an arbitrary path on
  purpose. A tunnel installed from anywhere else still runs, but has no entry in
  the WireGuard GUI — which leaves you with an always-on VPN and no way to
  switch it off.
</Callout>

### The kill switch

On Windows the kill switch is **WireGuard's own**, not something this project
installs. WireGuard for Windows blocks untunneled traffic whenever a tunnel
claims the whole address space, which the `AllowedIPs = 0.0.0.0/0, ::/0` in your
generated config does for both IPv4 and IPv6.

We deliberately do not write custom Windows Firewall or WFP rules on top of it.
WireGuard already implements this correctly, and a wrong custom rule can lock
you out of your own network with no easy way back.

What `setupclient.ps1` does instead is **verify** it took effect. After the
handshake succeeds it checks that both default routes actually point at the
WireGuard adapter:

```powershell
Get-NetRoute -DestinationPrefix 0.0.0.0/0 | Format-Table ifIndex, NextHop
Get-NetRoute -DestinationPrefix ::/0      | Format-Table ifIndex, NextHop
```

If IPv4 is captured but IPv6 is not, the script checks whether the machine has
IPv6 addresses at all — a missing `::/0` route is harmless on an IPv4-only
machine and a live leak on a dual-stack one, and it tells you which case you are
in. This reports only; it never fails the install.

<Callout type="warning">
  While the tunnel is active, traffic that cannot go through it is blocked
  rather than falling back — **LAN access included**. Deactivate the tunnel in
  the GUI to reach local printers, network shares, or your router's admin page.
</Callout>

### Manage the tunnel

Use **Activate / Deactivate** in the WireGuard GUI, or from an Administrator
PowerShell session:

```powershell
Get-Service   "WireGuardTunnel`$wg0"
Stop-Service  "WireGuardTunnel`$wg0"
Start-Service "WireGuardTunnel`$wg0"
```

```powershell
& "C:\Program Files\WireGuard\wg.exe" show wg0
```

## Phones and tablets

Phones and tablets cannot run the setup scripts, so they are added from the
server instead — without giving up the rule that a device's private key never
leaves it. The device generates its own keypair; the server only ever sees the
public half.

<Steps>

### Generate the keypair on the device

Install the official WireGuard app from the App Store or Google Play. Tap **+**,
choose **Create from scratch**, name the tunnel, and tap **Generate keypair** (on
Android, the generate button next to the private key). Copy the **public** key it
shows.

### Get the public key to the server

It is not secret, so any channel works — a message to yourself, an email, a
note. Never send the private key.

### Register it

On the server, from the repository root:

```bash
./add-device.sh <public-key>
```

It registers the key through the same API the client scripts use, prints the
values to enter, and shows the server's public key as a QR code.

### Fill in the tunnel

Enter the printed values:

| Section | Field | Value |
|---|---|---|
| Interface | Addresses | the address it printed, e.g. `10.13.26.7/32` |
| Interface | DNS servers | `172.29.144.30` |
| Peer (**Add peer**) | Public key | scan the QR code with the device's camera, copy, paste |
| Peer | Endpoint | `<server>:51820` |
| Peer | Allowed IPs | `0.0.0.0/0, ::/0` |
| Peer | Persistent keepalive | `25` |

Leave the other fields as they are. Save the tunnel and switch it on.

</Steps>

<Callout type="warning">
  On Android, leave **Exclude private IPs** unchecked. It would send the DNS
  server `172.29.144.30` around the tunnel, and name resolution would stop
  working.
</Callout>

What this keeps from the scripts' guarantees:

| | |
|---|---|
| **Private key** | Generated in the WireGuard app and never leaves the device |
| **Server identity** | You register over SSH, which already verifies the server, and its WireGuard key reaches the device through the camera rather than the network |
| **Registration token** | Never on the device — registration happens on the server |

The tunnel itself is the same one the scripts set up: an address from
`10.13.26.0/24`, Pi-hole for DNS, and `0.0.0.0/0, ::/0` so all traffic goes
through it. You turn it on and off with the tunnel's switch in the app.

**Kill switch.** On Android, open WireGuard in the system VPN settings and turn
on **Always-on VPN** and **Block connections without VPN**; traffic is then
blocked whenever the tunnel is not up. On iOS, the tunnel's **On-Demand**
settings can switch it on automatically.

To remove a phone later, follow [Removing a peer](#removing-a-peer) with the
address `add-device.sh` printed.

## How the script recognises your server

No CA-signed certificate is needed. `setup.sh` knows the certificate nginx
serves, so it writes that certificate's key fingerprint into both scripts, along
with the server's WireGuard public key:

| Server certificate | Client behaviour |
|---|---|
| Self-signed (default) | **Pinned.** CA and expiry checks are skipped, but any key other than the pinned one is refused |
| CA-signed | Validated normally against the system trust store; nothing is pinned, because a CA renewal may change the key |

On Linux the pin is `curl -k --pinnedpubkey sha256//<pin>`; on Windows the same
flags go to the built-in `curl.exe`, because `Invoke-RestMethod` can only
validate against the trust store or skip validation entirely. On a mismatch
curl aborts **before sending anything**, so an interceptor never sees the token.

Two layers, protecting different things:

- **The pin protects the token.** Only a server holding the pinned key receives
  the registration request.
- **The baked-in WireGuard key protects the tunnel.** The script builds its own
  config and takes only the assigned address from the reply, so even a forged
  reply cannot redirect the tunnel — WireGuard's handshake only completes with
  the server holding that key.

The pin changes only when `setup.sh` issues a new certificate (`--force`, or a
new address). Scripts rendered before that refuse to register and say so — fetch
fresh ones from `scripts/`. Devices already connected are unaffected; they never
talk to the registration API again.

<Callout type="warning">
  The script itself is now what proves your server's identity. Move it to the
  device over a channel you trust — `scp`, USB — not email or chat.
</Callout>

## Adding more clients

Run the script on each new computer — or `add-device.sh` for each phone or
tablet. Every device gets its own keypair and the next free address. The pool
holds **253 peers**, `10.13.26.2` through `10.13.26.254`, shared by all of them.

Re-running on a device that is *already* configured does not create a second
peer: both scripts detect the existing config. The Linux script turns the VPN
on; the Windows script opens the WireGuard GUI so you can activate the tunnel.

## Removing a peer

There is no deregistration endpoint, so removal is manual and takes two steps —
deleting the file alone leaves the peer live in the running interface until the
container restarts:

```bash
# on the server
cd ~/AutoGuard-VPN
grep -l '10\.13\.26\.X/32' peers/*.conf        # find the peer's file
PUB=$(awk '/PublicKey/{print $3}' peers/<file>.conf)
docker exec wireguard wg set wg0 peer "$PUB" remove
rm peers/<file>.conf
```

<Callout type="warning">
  Stale peer files consume addresses from the pool even when the client is long
  gone, because `allocate_ip()` derives the used set by scanning `AllowedIPs`
  lines in `peers/`. Clean up peers you have retired.
</Callout>
