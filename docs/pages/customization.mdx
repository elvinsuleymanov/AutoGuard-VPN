# Customization

Network topology lives in the variable block at the top of `setup.sh`. Edit it
**before** the first run — the values are written into `.env` and consumed by
Docker Compose at container creation.

<Callout type="warning">
  Edit `templates/`, never the rendered output. `setup.sh` re-renders
  `wireguard/wg_confs/wg0.conf`, `nginx/nginx.conf`, and `scripts/` from
  `templates/` on **every** run, so changes made to the generated files are
  silently discarded the next time you run it.
</Callout>

## Network addresses

```bash
# setup.sh — edit before running
SUBNET="172.29.144.0/24"   # Docker bridge subnet
IP_WG="172.29.144.10"
IP_UNBOUND="172.29.144.20"
IP_PIHOLE="172.29.144.30"
IP_NGINX="172.29.144.40"
IP_AUTH="172.29.144.50"
```

All five addresses must fall inside `SUBNET`. Compose drives its `ipam` block
from `${SUBNET}` in `.env`, so changing the variable here is sufficient — no
edit to `docker-compose.yml` is needed.

Changing any of these after the stack is running requires `docker compose down`
followed by `./setup.sh`, so the containers are recreated on the new addresses.

## VPN client subnet

```bash
INTERNAL_SUBNET="10.13.26.0"   # /24 assumed; the server takes .1
```

Clients get `10.13.26.2` through `10.13.26.254` — 253 peers.

<Callout type="warning">
  Existing files in `peers/` still reference the old range. After changing
  `INTERNAL_SUBNET`, delete them and re-register every client, or the allocator
  will hand out addresses that do not match the interface.
</Callout>

## WireGuard port

```bash
PORT_WG="51820"
```

`docker-compose.yml` publishes `${PORT_WG}:51820/udp` — only the **host** side
changes. The container always listens on `51820`, and generated client configs
use `PORT_WG` in their `Endpoint`. Update your cloud firewall to match.

## Interface name

```bash
INTERFACE_NAME="wg0"
```

Controls the interface name inside the container and in generated client
configs. `wg0` is the universal default; change it only for a specific reason.

## Restricting the API by country

The registration API is reachable from the whole internet by default, which
means it collects the same background scanning any public address does. Pass
`--geo-allow` with one or more ISO country codes to close it down:

```bash
./setup.sh --geo-allow az
./setup.sh --geo-allow az,tr,de
```

`setup.sh` downloads the aggregated CIDR list for each country and writes
`nginx/geo/allow.conf`. Sources outside the list get a bare connection close
(nginx `444`) with no response to fingerprint. Loopback, the Docker bridge and
the VPN subnet are always allow-listed, so the stack never blocks itself.

<Callout type="warning">
  This gates **only** the HTTPS registration API. The WireGuard port is
  untouched, so existing peers keep working from anywhere — but a client
  travelling outside the allow-listed countries cannot *register* until it is
  back. Omit the flag to allow all sources.
</Callout>

## NAT egress interface

The `PostUp`/`PostDown` rules masquerade out of `eth0`:

```ini
PostUp   = iptables -A FORWARD -i %i -j ACCEPT; iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE
PostDown = iptables -D FORWARD -i %i -j ACCEPT; iptables -t nat -D POSTROUTING -o eth0 -j MASQUERADE
```

<Callout type="info">
  **This is almost never what you need to change.** That rule runs *inside* the
  WireGuard container, and a container attached to a single user-defined bridge
  always sees its interface as `eth0`. Your host's egress name — `ens5` on AWS
  Nitro, `enX0` on Amazon Linux 2023, `enp0s3` elsewhere — is irrelevant here.
</Callout>

Confirm before changing anything:

```bash
docker exec wireguard ip link show
docker exec wireguard iptables -t nat -L POSTROUTING -n -v
```

If the interface genuinely is not `eth0`, edit
`templates/wg0.conf.template` — not the rendered config — then re-render:

```bash
./setup.sh && docker compose restart wireguard
```

## TLS certificate

By default `setup.sh` issues a self-signed certificate inside a throwaway
container, valid for 365 days:

```bash
openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout /tmp/privkey.pem -out /tmp/fullchain.pem \
  -subj "/CN=${PUBLIC_IP}" -addext "subjectAltName=IP:${PUBLIC_IP}"
```

The CN and SAN match the address nginx actually serves, and both PEMs are
streamed back over stdout for the host to write — a bind mount would leave
root-owned files behind and silently write nowhere under Docker Desktop. The
certificate is reissued automatically whenever the public IP changes.

The client scripts pin this certificate's key, so the self-signed default is
already safe against interception — a CA-signed certificate is optional. See
[Client Setup](/client-setup#how-the-script-recognises-your-server).

### Using a real certificate

<Steps>

### Install the files

Put your chain at `certs/fullchain.pem` and the key at `certs/privkey.pem`.
`setup.sh` leaves existing certificates alone unless `--force` is passed or the
public address changed.

### Point setup at your hostname

```bash
./setup.sh --public-ip vpn.example.com
```

A hostname is rendered into the nginx `server_name`, the WireGuard `Endpoint`,
and the client scripts.

### Re-render and redistribute

```bash
./setup.sh --public-ip vpn.example.com
```

Nothing to edit by hand. `setup.sh` inspects the certificate it is about to
serve and compares its issuer to its subject — they match only on a self-signed
certificate. It then renders TLS validation **on** in both client scripts and
tells you so:

```
✅ CA-signed certificate — client scripts will validate TLS normally.
```

Redistribute the regenerated `scripts/` to your clients.

</Steps>

<Callout type="info">
  The detection is deliberately not "did `setup.sh` issue this certificate?" —
  the reuse path cannot tell last run's self-signed certificate from one you
  installed yourself. Comparing issuer to subject asks the question that
  actually matters: is there anything here a client could validate against?
</Callout>

`certs/` is bind-mounted read-only into `nginx-proxy`; no Compose changes needed.

## Pi-hole

### Reaching the admin UI

The admin UI is published to `127.0.0.1:65231` on the host — it is **not**
reachable from the internet, by design. Two ways in:

```bash
# over the VPN, once your tunnel is up
http://172.29.144.30/admin
```

```bash
# or an SSH tunnel from your workstation
ssh -L 65231:127.0.0.1:65231 <user>@<server-ip>
# then open http://127.0.0.1:65231/admin
```

Retrieve the generated password:

```bash
grep WEBPASSWORD .env
```

<Callout type="error">
  Do not change the publish to `65231:80/tcp` to "make it easier to reach".
  Docker publishes ports by DNAT in `nat/PREROUTING`, which **bypasses the host
  `INPUT` chain** — a `ufw deny 65231` would give you no protection at all on an
  `0.0.0.0` bind. The loopback address in `docker-compose.yml` is the only thing
  keeping the admin UI private.
</Callout>

To move it to a different **loopback** port, edit the binding in
`docker-compose.yml` and keep the address prefix:

```yaml
ports:
  - "127.0.0.1:9090:80/tcp"
```

Then `docker compose up -d pihole`. The container-internal port stays `80`.

### Adding a blocklist

1. Open the admin UI and log in.
2. Go to **Lists** in the sidebar.
3. Paste a blocklist URL into **Address**, add a comment, click **Add**.
4. Run **Tools → Update Gravity** to download and compile.

Or from the server:

```bash
docker exec pihole pihole -g
```

### Recommended lists

| List | URL | Focus |
|---|---|---|
| StevenBlack Unified | `https://raw.githubusercontent.com/StevenBlack/hosts/master/hosts` | Ads + malware |
| AdGuard DNS Filter | `https://adguardteam.github.io/AdGuardSDNSFilter/Filters/filter.txt` | Ads + trackers, low false positives |
| HaGeZi Multi PRO | `https://raw.githubusercontent.com/hagezi/dns-blocklists/main/adblock/pro.txt` | Comprehensive, actively maintained |
| EasyList | `https://v.firebog.net/hosts/Easylist.txt` | Standard ad networks |
| Phishing Army | `https://phishing.army/download/phishing_army_blocklist_extended.txt` | Phishing domains |

<Callout type="info">
  Start with one or two. Running many at once works but lengthens gravity
  compile time and increases the chance of a false positive you then have to
  hunt down.
</Callout>

### Blocking and allowing individual domains

```bash
docker exec pihole pihole --blacklist ads.example.com
docker exec pihole pihole --blacklist --wildcard example.com   # and subdomains
docker exec pihole pihole --white-list cdn.example.com
```

Allow-listed domains override every blocklist, including gravity.

### Diagnosing a blocked domain

```bash
docker exec pihole pihole --query ads.example.com
```

Shows which lists the domain appears in — the fastest way to identify which
blocklist is causing a false positive.

## Unbound

Unbound's config is bind-mounted from `unbound/`. Edit `unbound/unbound.conf`
and restart:

```bash
docker compose restart unbound
```

The shipped config allocates roughly 500 MB of cache
(`msg-cache-size` + `rrset-cache-size`). On a 1 GB host, lower both to `32m` and
`64m` before starting the stack — see [Requirements](/requirements).
