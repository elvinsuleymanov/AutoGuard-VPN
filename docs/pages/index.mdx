## Why run your own

A commercial VPN moves your traffic from an ISP you did not choose to a company
you cannot audit. AutoGuard VPN removes the third party entirely: you hold the
server keys, the DNS resolver is yours, and no query leaves your infrastructure
to a public resolver.

## Quick start

<Steps>

### Bring up the server

On any Docker host with a public IPv4 address:

```bash
git clone https://github.com/ElvinSuleymanov/AutoGuard-VPN.git
cd AutoGuard-VPN
chmod +x setup.sh
./setup.sh
```

`setup.sh` generates the server keypair, issues a TLS certificate, renders every
config from `templates/`, and starts the stack. Docker and Docker Compose are
the only things the host needs — key and certificate generation happen inside a
throwaway `alpine` container.

### Open two ports

`443/tcp` for the registration API and `51820/udp` for the tunnel itself. On AWS
that is a security-group rule; elsewhere it is your cloud firewall. Pi-hole's
admin UI deliberately needs no rule — it binds to loopback only.

### Connect a client

`setup.sh` writes `scripts/setupclient.sh` and `scripts/setupclient.ps1` with
your registration token already embedded. Copy the one you need to the client
and run it with root or Administrator rights:

```bash
sudo ./setupclient.sh          # Linux
```

```powershell
.\setupclient.ps1              # Windows, as Administrator
```

The client generates its own keypair, registers the public half, writes the
config, and brings the tunnel up.

For a phone or tablet, generate the keypair in the WireGuard app and run
`./add-device.sh <public key>` on the server — see
[Phones and tablets](/client-setup#phones-and-tablets).

</Steps>

<Callout type="warning">
  The client scripts contain a live registration token. They are gitignored for
  that reason — distribute them over a channel you trust, and rotate with
  `./setup.sh --force` if one leaks.
</Callout>

Registration happens once, over HTTPS. After that the client talks only to the
WireGuard port, and its DNS resolves through Pi-hole into Unbound.

## What's in the stack

| Service | Image | Address | Reachable from | Role |
|---|---|---|---|---|
| `wireguard` | built locally | `172.29.144.10` | internet, `51820/udp` | Tunnel server, hot peer reload |
| `nginx-proxy` | `nginx:1.27-alpine` | `172.29.144.40` | internet, `443/tcp` | TLS termination for the API |
| `auth-service` | built locally (FastAPI) | `172.29.144.50` | bridge only | Peer registration, IP allocation |
| `pihole` | `pihole/pihole` | `172.29.144.30` | VPN + `127.0.0.1:65231` | Ad-blocking DNS, admin UI |
| `unbound` | `mvance/unbound` | `172.29.144.20` | bridge only | Recursive DNSSEC resolver |

Clients receive addresses from `10.13.26.0/24` starting at `10.13.26.2`, so a
single deployment holds up to 253 peers. The server itself is `10.13.26.1`.

<Callout type="info">
  Only two ports face the internet. Pi-hole's admin UI is published to
  `127.0.0.1:65231` on purpose — published Docker ports are DNAT'd before the
  host `INPUT` chain, so a firewall rule would not protect an `0.0.0.0` bind.
  The loopback address is the control. See [Requirements](/requirements).
</Callout>
