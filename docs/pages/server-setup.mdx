# Server Setup

`./setup.sh` brings up the entire stack. It is the only command you run on the
server.

```bash
git clone https://github.com/ElvinSuleymanov/AutoGuard-VPN.git
cd AutoGuard-VPN
chmod +x setup.sh
./setup.sh
```

## Command-line flags

| Flag | Effect |
|---|---|
| `--force`, `-f` | Rotate the server keypair, registration token, and Pi-hole password. **Invalidates every client config already issued.** |
| `--public-ip <addr>` | Use this address instead of detecting and prompting. Accepts a hostname. |
| `--geo-allow <cc,…>` | Restrict the registration API to the given ISO country codes, e.g. `--geo-allow az,tr`. Everything else gets a bare connection close. Omit to allow all sources. |
| `--render-only` | Generate keys, certificates, `.env` and all rendered configs, then stop without starting the stack. |
| `--help`, `-h` | Print usage and exit. |

## Re-running is safe

`setup.sh` is idempotent. Every generated file is rendered fresh from
`templates/` on each run, and the secrets already in `.env` are reused — so the
token baked into your client scripts never drifts out of sync with the one
`auth-service` validates against.

<Callout type="warning">
  `--force` is the exception. It rotates the keypair, the registration token and
  the Pi-hole password, which breaks every client config already handed out.
  Use it when you believe a token has leaked, not as a general "clean run".
</Callout>

Two things stop a re-run from silently doing nothing, and both are easy to get
wrong:

- `docker compose up -d` will not recreate a container whose only change is the
  *content* of a bind-mounted config file, so a re-run explicitly restarts
  `wireguard` and `nginx-proxy` to pick up freshly rendered configs.
- `up -d` also builds only when an image is **missing**, never because the source
  changed. `setup.sh` therefore passes `--build`, so a `git pull` that touches
  `auth/` or `wireguard/` actually ships on the next run.

Between them, `git pull && ./setup.sh` is the whole update procedure. You should
never need to run a `docker compose` command by hand.

## What it does, step by step

<Steps>

### Dependency check

Verifies `docker` is in `PATH`, that `docker compose version` succeeds (falling
back to a legacy `docker-compose` binary), that the daemon is reachable, and
that `templates/` exists so you are running from the repository root.

Docker and Compose are the **only** host requirements. Key generation and
certificate issuance both run inside a disposable `alpine:3.20` container.

### Timezone detection

```bash
tz=$(timedatectl 2>/dev/null | awk '/Time zone/ {print $3}')
[ -z "$tz" ] && tz=$(cat /etc/timezone 2>/dev/null || echo "UTC")
```

Written to `.env` as `DETECTED_TZ` and consumed by the Pi-hole container so its
query log timestamps match the host.

### Public IP detection

```bash
curl -s --max-time 5 https://ifconfig.me/
```

You are prompted to confirm or override the result; `--public-ip` skips the
prompt entirely. The value becomes the WireGuard `Endpoint` in every client
config, the nginx `server_name`, and the certificate's CN and SAN.

### Secret generation

```bash
random_hex() { head -c 32 /dev/urandom | od -An -tx1 | tr -d ' \n'; }
random_b64() { head -c 12 /dev/urandom | base64 | tr -d '\n'; }
```

Straight from the kernel CSPRNG — no `openssl` on the host. `REGISTRATION_TOKEN`
is the `X-Auth-Token` value clients must present to `/addnewpeer`. Existing
values in `.env` are reused unless `--force` is passed.

### WireGuard X25519 keypair

Generated in a throwaway container and streamed back over stdout:

```bash
docker run --rm alpine:3.20 sh -ec '
    apk add --no-cache openssl >/dev/null 2>&1
    pem=$(mktemp)
    openssl genpkey -algorithm X25519 -out "$pem" 2>/dev/null
    openssl pkey -in "$pem" -outform DER          | tail -c 32 | base64
    openssl pkey -in "$pem" -pubout -outform DER  | tail -c 32 | base64
    rm -f "$pem"
'
```

Persisted to `wireguard/keys/server_private.key` (mode `600`) and
`server_public.key` (mode `644`), then reused on later runs. Persisting the
private key is what keeps `wg0.conf` and the public key handed to clients
derived from the same secret.

### Self-signed TLS certificate

```bash
openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout /tmp/privkey.pem -out /tmp/fullchain.pem \
  -subj "/CN=${PUBLIC_IP}" -addext "subjectAltName=IP:${PUBLIC_IP}"
```

Also generated in a container, with both PEMs streamed back over stdout for the
host to write. Bind-mounting `certs/` into the container would work on Linux but
writes nowhere the host can see under Docker Desktop, and leaves root-owned
files behind — streaming keeps ownership and modes in the host's hands.

Reissued automatically when the certificate is missing, `--force` is passed, or
the public address changed.

<Callout type="info">
  The client scripts pin this certificate: `setup.sh` computes the SHA-256 of
  its public key and writes it into both scripts, which then refuse any other
  key before sending the registration token. The run prints the fingerprint as
  `sha256//<pin>`. Because the key is pinned rather than the certificate, its
  365-day expiry does not affect registration.
</Callout>

### Rendering the configs

Every generated file comes from `templates/` through a single `render()` helper
that substitutes placeholder/value pairs into a temp file and moves it into
place. The templates themselves are never modified, which is what makes repeated
runs safe.

| Template | Rendered to |
|---|---|
| `wg0.conf.template` | `wireguard/wg_confs/wg0.conf` (mode `600`) |
| `nginx.conf.template` | `nginx/nginx.conf` |
| `setupclient.sh.template` | `scripts/setupclient.sh` |
| `setupclient.ps1.template` | `scripts/setupclient.ps1` |

`proxy_pass http://auth-service:5000` is left as a service name — Docker's
embedded DNS resolves it on the user-defined bridge, so hardcoding a container
IP would only make the config brittle.

<Callout type="info">
  `ListenPort` stays `51820`: that is the port *inside* the container. The
  host-side port comes from the `${PORT_WG}:51820/udp` publish in
  `docker-compose.yml`.
</Callout>

### Building the geo allow-list

Writes `nginx/geo/allow.conf`, which the nginx `geo` block includes. Without
`--geo-allow` it contains a single `0.0.0.0/0 1;` line and everything is
permitted. With it, `setup.sh` downloads the aggregated CIDR list for each
country code and always prepends loopback, the Docker bridge and the VPN subnet
so the stack cannot block itself.

### Writing .env

All configuration lands in `.env` with mode `600`:

| Variable | Default |
|---|---|
| `SUBNET` | `172.29.144.0/24` |
| `INTERNAL_SUBNET` | `10.13.26.0` |
| `IP_WG` | `172.29.144.10` |
| `IP_UNBOUND` | `172.29.144.20` |
| `IP_PIHOLE` | `172.29.144.30` |
| `IP_NGINX` | `172.29.144.40` |
| `IP_AUTH` | `172.29.144.50` |
| `PORT_WG` | `51820` |
| `PORT_AUTH` | `5000` |
| `PUBLIC_IP` | detected or `--public-ip` |
| `WEBPASSWORD` | generated |
| `REGISTRATION_TOKEN` | generated |
| `DETECTED_TZ` | detected |

Secrets are scoped per service rather than handed to every container through
`env_file`, so `REGISTRATION_TOKEN` is visible to `auth-service` alone.

<Callout type="error">
  `.env` is generated, not committed. Running `docker compose up` before
  `setup.sh` fails on undefined variables. Always run `setup.sh` first.
</Callout>

### Starting the stack

```bash
docker compose up -d --build --wait
```

`--build` is what makes "just re-run `setup.sh`" true after a `git pull`. Plain
`up -d` builds only when an image is **missing**, so a changed `auth/` or
`wireguard/` would keep running the old image and your update would silently not
ship. Layers are cached, so a run with nothing to rebuild costs seconds.

`--wait` blocks until every service reports healthy, and `depends_on` with
`condition: service_healthy` enforces the order:

```
unbound (healthy)
  └── pihole (healthy)
        └── wireguard (healthy)
              └── auth-service (healthy)
                    └── nginx-proxy (healthy)
```

If any service never becomes healthy the script exits and points you at
`docker compose logs`.

</Steps>

## Verifying the deployment

```bash
docker compose ps                                    # all five (healthy)
docker exec wireguard wg show wg0                    # interface up, peers listed
docker exec nginx_proxy curl -sk https://localhost/health
grep WEBPASSWORD .env                                # Pi-hole admin password
```

Pi-hole's admin UI is bound to `127.0.0.1:65231`. Reach it over the VPN at
`http://172.29.144.30/admin`, or tunnel in:

```bash
ssh -L 65231:127.0.0.1:65231 <user>@<server-ip>
```

## Starting over

To wipe the deployment and rebuild from nothing. Order matters — `down` needs
`.env` to resolve its variables, so tear the stack down *before* deleting it:

```bash
docker compose down --remove-orphans --rmi local
sudo rm -rf .env certs peers etc-pihole scripts nginx \
            wireguard/keys wireguard/wg_confs
./setup.sh
```

`sudo` is needed because Pi-hole and WireGuard write into those directories as
root. Do **not** delete `wireguard/` or `unbound/` wholesale — they hold tracked
files. Deleting `.env` rotates every secret, so all existing clients must
re-register.
